# 선언형 애플리케이션 진입과 수명

LVUI의 `Application` 선언을 네이티브 앱 진입과 창에 연결하는 계약이다.

## 계약

`.lvui`의 `Application`은 하나 이상의 창을 소유하는 앱의 최상위 선언이다.
`Application { ApplicationWindow { ... } }`와 같은 선언을 지원한다. 직계 자식은 하나 이상의 `Scene`, `Window` 또는 `ApplicationWindow`여야
하며 조건부·반복 장면, 중첩 앱, 알 수 없는 앱 입력은 컴파일 오류이다. `Scene`은
한 네이티브 창과 지역 뷰 세션을 소유한다. 명시적 장면 선언과 C++ 메타데이터는
[Scene 계약](Scenes.md)을 따른다. 기존의
`Window` 루트는 독립적으로 마운트할 수 있는 뷰로 계속 지원한다.

## 앱과 창의 소유권

앱 최상위와 `Application` 본문의 가변 상태와 `import` 백엔드는 앱 스코프가
소유한다. 스칼라 `const`는 컴파일할 때 결정된다. Core가 네이티브 드라이버를
시작하기 전에 앱 스코프를 한 번 활성화하고, 각 창 스코프는 이를 차용한다.
창 본문의 백엔드와 상태는 해당 창 스코프가 별도로 소유한다. 창 뷰를 분리하고
다시 구성하면 앱 상태는 유지되고 창 상태는 새로 만들어진다. 이름 있는 보조
창은 네이티브 창을 닫은 뒤에도 새 창 스코프로 다시 열 수 있다.

앱 종료 시 Core가 소유한 작업을 정리한 다음 창을 분리하고 앱 스코프를
퇴역시킨다. 앱 백엔드의 생성에 실패하면 드라이버를 시작하지 않고 부분적으로
활성화된 앱 스코프를 정리한다. 창 뷰의 부착 실패가 앱 스코프를 직접 파괴하지는 않으며,
활성 창이 차용 중인 앱 스코프의 조기 퇴역은 거부된다. 스코프의 활성화와
퇴역은 소유 스레드에서 수행해야 한다. 외부 작업 실행기와 해당 작업의 수명은
이를 제공한 쪽이 관리해야 한다.

독립 `build` 호출은 앱 스코프를 자체 생성해 뷰와 함께 보유한다. Core에 연결한
앱은 Core의 수명 동안 앱 스코프를 보유하며, 창을 열 때 해당 스코프를 빌린다.
독립 `build`는 첫 창만 구성하며 앱 실행을 대신하지 않는다. 독립 빌드는 창
레지스트리를 설치하지 않으므로 `openWindow`와 `closeWindow`를 사용할 때는
Core에 연결된 앱 구성이 필요하다.

## 선언형 다중 창

iOS에서 `lvui_add_application`은 기본적으로 iiGUI 장면 델리게이트와 다중 장면
지원이 포함된 번들 매니페스트를 제공한다. 앱은 타깃의
`MACOSX_BUNDLE_INFO_PLIST`를 지정해 문서 형식·URL 체계·권한 등의 자체 설정으로
대체할 수 있으며, 대체 매니페스트의 장면 설정은 앱이 관리한다. 설치된 LVUI의
빌드 함수도 같은 기본 매니페스트를 사용한다. 운영체제나 앱 설정이 실제 다중 장면을
허용하지 않으면 창 요청은 `unsupported`로 실패한다.

Android에서 `lvui_add_application`은 일반 실행 파일 대신 NativeActivity가
불러올 공유 라이브러리를 만든다. 생성된 앱 구성은 iiGUI의 Android 진입
어댑터를 통해 Core 앱 수명에 연결된다. Android용 iiGUI의
`iiGUI::AndroidEntry` 타깃이 필요하며 구버전 패키지에는 명확한 구성 오류를
반환한다. 매니페스트·리소스·APK의 구성과 서명은 앱이 별도로 담당한다.
Android 호스트는 현재 단일 창만 지원한다.
2026-11-05 Android NDK r30과 API 24 arm64를 대상으로 Core·iiGUI·LVUI를
별도 스테이징하고, 설치된 LVUI 빌드 함수와 호스트 컴파일러로 선언형 앱의
공유 라이브러리를 정적·공유 iiGUI 구성에 각각 생성·링크했다. NativeActivity와
앱 진입 심볼, Core 앱·iiGUI 호스트 구현 및 전이 공유 라이브러리의 Qt·LVRS
비의존성을 검사했다. 이 결과는
APK 생성, OS 창 표시 또는 기기 실행의 증거가 아니다.
이후 같은 Android 대상의 설치된 iiGUI 예제에서 선택적 OS·렌더 검사 소스도
활성화하여 LVUI 및 iiSDK 설치본과 컴파일·링크했다. 실제 기기 검사는 수행하지 않았다.

교차 컴파일에서는 대상 플랫폼용 런타임을 빌드하며 `lvui-check`와
`lvui-compile` 실행 파일은 기본으로 빌드하지 않는다. 선언 파일의 AOT 생성에는
호스트에서 실행 가능한 별도 `LVUI_HOST_COMPILER`를 지정한다. 대상 플랫폼에 배포할
컴파일러 실행 파일이 별도로 필요하면 `LVUI_BUILD_COMPILER_TOOLS`를 명시적으로
켜서 빌드할 수 있다. 이 옵션이 꺼진 구성에서는 LVUI 프로젝트의 테스트를 등록하지
않으므로, 실행 가능한 호스트 구성에서 해당 테스트를 별도로 실행한다.

### 독립 창 드라이버 계약

다중 창 앱은 창과 앱 드라이버의 수명을 분리한다. 네이티브
앱 드라이버는 선언된 창과 별도로 이벤트 루프를 보유하며, 첫 창을 포함한 각
창은 독립 세대로 열린다. 하나의 창을 닫아도 다른 열린 창과 앱 스코프, 파일
요청 및 창 열기 명령은 유지한다. 마지막 창의 닫기는 앱의 종료 승인 콜백을
거친다. 승인이 거부되면 그 창을 유지하고, 승인이 허용되면 새 창 요청을 막은
뒤 네이티브 콜백이 반환된 다음 앱 드라이버를 종료한다. 명시적 앱 종료도 같은
승인 계약을 따른다.

창 생성 중인 세대도 살아 있는 창으로 계산한다. 닫힘이 승인된 세대는 다른
닫기 판단에서 제외하되, 늦게 도착한 이전 세대의 닫힘 통지가 새 세대를 퇴역시키지
못해야 한다. 같은 창의 재진입 종료 요청은 거부한다. 창이 예기치 않게 강제로
닫혀 마지막 창이 사라지면 앱 종료 승인을 별도로 시도하며, 거부된 경우 앱은
창 없이 유지될 수 있다. 네이티브 창이 실제로 파괴된 뒤에는 닫기를 취소할 수
없다. 현재 이 드라이버의 구현 경로는 macOS Cocoa, Windows Win32, Linux의
X11·Wayland와 iPadOS UIKit이다. Wayland 다중 창은 소스와 모의 호스트로,
UIKit은 헤드리스 라우터와 iPhoneOS 앱 링크로 검증한 상태이다.
지원하지 않는 호스트의 다중 창 앱은 구성 시 `unsupported`를 반환한다.

`Application`의 직계 자식으로 하나 이상의 무조건적인
`Scene`, `Window` 또는 `ApplicationWindow`를 선언한다. 첫 창을 포함한 모든 창은
별도의 앱 드라이버와 동일한 이벤트 루프를 공유한다. 모든 창은 앱 스코프를 공유하지만 창별 선언과
위젯 ID는 서로 독립적이다. 처음 열도록 선언된 창이 모두 부착된 뒤 `onReady`를 한 번 전달한다.
준비를 전달하기 직전 모든 호스트의 현재 상태도 확인하므로, 닫힘 콜백의 전달이
지연되어도 이미 닫힌 창을 준비된 창으로 계산하지 않는다.
독립 드라이버 또는 보조 창을 지원하지 않는 호스트는 조용히 생략하지 않고
`unsupported`를 반환한다. 창의 비동기 부착 오류는 기록되며 창 뷰 분리 중 발생한
오류보다 우선해 앱 실행 결과에 전달된다. 초기 창이 준비되기 전에 예기치 않게
닫히면 앱 시작 오류이며 정상적인 앱 종료 중에 닫히면 오류로 취급하지 않는다.
조건부·반복 창은 아직 구현되지 않았다.
창 호스트가 준비 이전이나 이후에 내부 오류를 처음 기록하면 iiGUI의 실패
핸들러가 이를 동기적으로 수신한다. LVUI는 오류를 보관하고 이벤트 루프를 중단한 뒤
창 정리 결과보다 우선해 앱 결과에 전달한다. 정상 닫힘은 오류를 만들지 않는다.
각 API가 즉시 반환한 오류는 그 호출자가 직접 처리해야 한다. Core 드라이버에서
별도로 기록된 오류와 보조 호스트 오류 사이의 전역 발생 순서는 보장하지 않는다.
다중 창 앱은 `IIGUI_HOST_APPLICATION_DRIVER_API`,
`IIGUI_HOST_FAILURE_HANDLER_API`와 `Host::set_failure_handler`를
제공하는 iiGUI 헤더·라이브러리가 필요하다. 기능이 없는 헤더는 컴파일 오류로,
이전 라이브러리는 링크 오류로 구분한다.

### 이름이 있는 창 명세

`Application`의 `Window`에 고유한 정적 `id`를 지정하고
`initiallyOpen: false`를 주면 앱 시작 시 열지 않는다. 기본값은 `true`이다.
`openWindow("id")`와 `closeWindow("id")`를 UI 또는 앱 이벤트의 콜백으로
사용하면 같은 다중 창 앱의 해당 창을 열거나 닫도록 요청한다. 대상에는 문자열
상수뿐 아니라 `openWindow(vm.selectedWindow)`처럼 문자열을 반환하는 반응형
표현식도 사용할 수 있다. 첫 창도 이름이
있으면 다른 창이 열린 동안 같은 방식으로 다시 열 수 있다. 첫 창은 앱 시작 시
열려 있어야 하며 단일 창 앱의 첫 창은 이 명령의 대상이 아니다. 창 선언의 중복
이름·동적 이름이나 첫 창의 지연 열기는 컴파일 오류이다. 선언된 이름은 NUL이 없는
비어 있지 않은 정적 UTF-8 문자열이며 최대 1024바이트이다. 상수 대상의 이름은
컴파일할 때 확인한다. 동적 대상은 소유 스레드의 이벤트 콜백에서 한 번 평가하고,
그 시점에 등록된 창이 아니면 오류로 전달하며 요청을 접수하지 않는다. 이벤트가
전달하는 인자는 대상 표현식과 별개이며 자동으로 창 이름에 사용하지 않는다.

동적 대상을 평가하기 전에 앱에서 현재 창·중첩 콘텐츠까지의 파생값을 바깥 스코프부터
갱신한다. 대상 표현식과 그 안의 명시적 메서드 호출은 버튼 생성이나 상태 변화가
아니라 이벤트가 발생했을 때 평가한다. 접수된 요청은 그때 선택된 창을 가리키므로 대기 중
원본 값이 변경되어도 다른 창으로 이동하지 않는다. 문자열이 아닌 C++ 대상은 생성된
C++의 타입 검사에서 거부한다. 닫힌 활성화의 콜백은 대상을 평가하거나 요청하지 않는다.
대상을 계산하거나 문자열로 변환하는 사용자 코드가 실행 중 현재 활성화를
퇴역시키더라도 그 결과로 새 창 요청을 접수하지 않는다.

요청은 소유 이벤트 루프에 접수해 현재 콜백이 끝난 뒤 처리한다. 이미 열린 창을
다시 열라는 요청과 이미 닫힌 창을 닫으라는 요청은 성공적인 무동작이다. 닫힌
창을 다시 열 때는 새 네이티브 호스트와 창 스코프를 만들고 앱 스코프는 유지한다.
접수 실패는 호출 오류이며, 접수 이후 호스트 생성·부착의 실패는 앱 수명 오류로
전달한다. 앱 종료 중에는 새 요청을 거부하고 남은 대기 작업은 실행하지 않는다.
처음 열도록 선언된 창만 앱의 초기 `onReady`를 기다리는 대상이다. 마지막 창의
닫기가 승인되거나 명시적 앱 종료가 승인되면 창 요청의 접수를 중단하고, 네이티브
닫기 콜백이 반환된 뒤 앱 드라이버와 남은 창을 정리한다. 실제 OS 창 실행 검증은
헤드리스 수명 검사와 별도이다.

```lvui
Application {
    import vm WindowSelector
    Window { PushButton(text: "Open", onClick: openWindow(vm.selectedWindow)) }
    Window(id: "tools", initiallyOpen: false) {
        PushButton(text: "Close", onClick: closeWindow("tools"))
    }
}
```

### 창별 수명 이벤트 명세

`Application`의 각 `Window` 또는 `ApplicationWindow`에는 인자 없는
`onOpened`와 `onClosed` 콜백을 선언할 수 있다. 콜백은 해당 창의 지역 백엔드와
공유 앱 스코프를 참조한다. `onOpened`는 창 뷰가 성공적으로 게시된 뒤 소유
스레드에서 한 번 전달한다. 처음 열리는 창의 이벤트는 앱 `onReady`보다 먼저
발생하며 나중에 연 창의 이벤트는 준비 이후에 발생할 수 있다.
`onClosed`는 게시된 창 뷰가 해제될 때 해당 창의 바인딩과 백엔드를 정리하기 전에
한 번 전달한다. 게시 전 생성에 실패하거나 게시 전에 해제된 창에는 닫힘 이벤트를
전달하지 않는다. 정상적인 개별 창 닫기와 앱 종료에 따른 창 정리 모두에
같은 규칙을 적용한다. 이벤트 콜백 실행 중 창이 닫히면 닫힘 이벤트가 중첩되어
전달될 수 있지만 중복 전달하지 않는다.
닫히는 창의 지역 뷰와 중첩 콘텐츠가 보유한 모든 표시 효과는 닫힘 콜백 전에
퇴역시킨다. 파생값과 창·앱 백엔드는 콜백이 끝날 때까지 유지하며 다른 창의
표시 효과는 퇴역시키지 않는다. 효과 퇴역에 실패하면 오류를 보존하고 나머지
그래프의 정리와 닫힘 콜백을 계속 시도한다.

콜백 예외는 최초 창 이벤트 오류로 보존하고 앱 이벤트 루프를 중단한다. 앱 시작
중 오류는 준비 이벤트를 막고, 종료 중 오류도 정리를 계속한 뒤 앱 실행 결과로
반환한다. 단독 `Window` 뷰 루트에서는 이 이벤트를 지원하지 않고 진단한다.
독립 `build`에서는 창 뷰의 게시·해제가 이벤트 경계이며 앱 실행이나 실제 OS 창의
생성을 대신하지 않는다. 독립 빌드의 반환값 없는 해제 훅에서는 오류를 호출자에게
반환할 수 없다.

```lvui
Application {
    import editor EditorBackend
    Window(onOpened: editor.windowOpened, onClosed: editor.windowClosed) {
        Label(text: editor.title)
    }
}
```

창 이벤트가 있는 생성 코드는
게시 완료를 알리는 iiGUI `IIGUI_COMMITTED_PUBLICATION_API`와 표시 효과를 먼저
퇴역시키는 LVUI `LVUI_BINDINGS_RETIRE_EFFECTS_API`를 요구한다. 대응 헤더가 없는
구버전은 컴파일 오류로 진단하며, 이전 바이너리와의 링크 가능성을 보장하지 않는다.

```lvui
Application {
    Window(title: "Canvas") { Label(text: "Canvas") }
    Window(title: "Tools") { Label(text: "Tools") }
}
```

지원 여부는 iiGUI의 `host_capabilities().secondary_windows`와
`supports_application_driver()`로 확인한다. 이 값은
컴파일된 호스트 계약이며 OS 세션과 개별 창 생성 성공을 보장하지 않는다. 현재
Cocoa·Win32·X11·Wayland·UIKit은 보조 창을 광고하며 Android·Web은 광고하지 않는다.
지원하지 않는 호스트에서는 앱 구성을 시작하기 전에 `unsupported`가 반환된다.
UIKit은 앱 매니페스트와 기기가 다중 장면을 허용하는지 창 요청 시 추가 확인한다.
세션의 연결 해제와 재연결은 같은 프로세스의 창 상태를 유지하지만, 프로세스 종료
후 상태 복원은 제공하지 않는다. 상세 계약과 플랫폼 검증 범위는
[iiGUI iPadOS 호스트](../../iiGUI/docs/IPADOS.md)를 따른다.
UIKit의 운영체제 관리 장면에서는 최초 창 크기 선언이 네이티브 크기 변경을
강제하지 않는다. 따라서 반응형 제목이나 외관이 고정된 초기 크기와 함께 있어도
뷰를 게시할 수 있으며, 게시 이후의 명시적 크기 변경은 별도로 거부된다.

## 앱 이벤트 명세

앱 이벤트는 `Application(onStart: vm.start, onReady: vm.ready,
onActive: vm.active, onInactive: vm.inactive, onStop: vm.stop)`과 같이 인자가
없는 콜백을 참조한다. 명시적 콜백 타입은 `Void`
반환이어야 하며 직접 참조한 C++ 메서드의 반환값은 사용하지 않는다. 시작·준비·종료 이벤트는
소유 스레드에서 한 번만 전달한다. `onStart`는 앱 스코프 초기화 후 드라이버 진입
전에, `onReady`는 처음 열도록 선언된 모든 창 뷰가 성공적으로 부착된 뒤에 전달한다. `onStop`은 성공적으로
시작한 앱의 모든 창 뷰가 분리된 뒤 바인딩과 백엔드를 정리하기 전에 전달한다.
시작 콜백의 실패는 드라이버 진입을 막고 부분 상태를 정리한다. 준비 콜백이 실패하면
창을 분리하고 종료 콜백을 전달하며 최초 오류를 유지한다. 종료 콜백이 실패해도
나머지 정리는 계속한다. 시작에 실패한 경우 종료 콜백은 전달하지 않는다.
콜백 실행 중 재진입은 거부한다. 독립 뷰 빌드에는 주 창 부착 완료를 나타내는
`onReady`가 없으며 앱 소유자 생성·정리에 대응하는 시작·종료 이벤트만 전달된다.
독립 뷰 빌드의 종료는 반환값이 없는 호스트 정리 훅에서 이루어지므로, 이때 발생한
`onStop` 예외는 정리 후 호출자에게 반환되지 않는다. Core에 연결된 앱은 종료 오류를
`Application::exec()`의 결과로 보고한다. 운영체제별 앱 중단·복원과 열린 문서의
장면 이벤트는 아직 별도 구현이 필요하다.

네이티브 호스트가 닫혔지만 운영체제 드라이버가 아직 반환하지 않은 경우,
iiSDKCore의 `driver_stopped()` 완료 신호는 소유 작업과 창을 먼저 정리하고
`onStop`을 전달한다. 완료 신호는 네이티브 콜백이 모두 끝난 뒤 소유 스레드에서
전달해야 하며 같은 신호의 반복은 종료 이벤트를 다시 발생시키지 않는다. UIKit은
iiGUI가 이를 메인 큐에 이연하여 전달한다. 운영체제의 강제 종료나 중단으로 큐가
실행되지 않는 상황까지 보장하지 않는다.

이벤트 참조는 뷰와 같은 방식으로 앱 스코프의
백엔드 메서드 또는 콜백을 사용하며, 이벤트에서 변경한 관측 값은 창에 반영된다.

### 전경·백그라운드 앱 이벤트 명세

`Application(onForeground: vm.foreground, onBackground: vm.background)`는 앱 스코프의 인자 없는 콜백이다.
플랫폼의 전경·백그라운드 신호를 전달하며 `onActive`·`onInactive`의 포커스
상태와 합성하거나 서로를 대신하지 않는다. 준비 전 각 상태의 마지막 값은 `onReady`
성공 후 전달한다. 준비 이후에는 상태별 중복을 생략하고 접수 순서를 지킨다.
같은 앱 이벤트 안에서 다시 접수된 상태와 파일 요청도 무한 재진입하지 않도록
기존 한도를 적용한다. 종료가 승인되면 남은 상태를 폐기하고, 거부되면 처리한다.
콜백 오류는 원인을 보존하고 앱 종료 결과로 전달한다.

UIKit의 앱 전체 전경·백그라운드, Android NativeActivity의 시작·중지와 Web
문서 표시 상태를 iiGUI가 전달한다. Cocoa와 Win32는 표시 중이고 최소화되지 않은
iiGUI 창이 하나 이상 있는지, X11은 매핑된 창이 하나 이상 있는지 앱 단위로
집계한다. X11의 상태는 창 관리자의 매핑·매핑 해제 알림에 의존하며 첫 창의
상태 알림 전에는 임의의 상태를 전달하지 않는다. 운영체제별 의미가 같거나
백그라운드 실행 권한이 보장된다는 뜻은 아니다. 해당 신호를 제공하지 않는 Wayland에서
이 이벤트가 선언된 앱은 구성 시 `unsupported`를 반환한다. 강제 종료나 운영체제의
즉시 중단에 대비한 영속성은 앱이 별도로 관리한다.
이 이벤트를 선언한 앱은 `IIGUI_HOST_APPLICATION_FOREGROUND_API`와
`Host::set_application_foreground_handler`를 제공하는 iiGUI를 요구한다. 이전
헤더는 컴파일 시 거부하고, 이전 라이브러리는 링크 시 구분한다.

### 종료 요청 승인과 선언형 종료 명령

`Application(onCloseRequested: vm.canClose)`는 마지막 창 또는 앱 종료 요청을 처리하기 전에
인자 없는 C++ 콜백을 소유 스레드에서 호출한다. 콜백은 `bool`을 반환하며
`true`는 종료를 허용하고 `false`는 현재 요청을 거부한다. 명시적 함수 타입은
`() -> Bool`이어야 한다. 기본값은 허용이다. 앱 스코프가 아직 생성되지 않은
초기 종료는 허용하며, 다른 앱 수명 콜백이 실행 중인 재진입 요청은 거부한다.

거부된 요청은 앱과 창을 유지하고 파일·활성 상태 및 보조 창 요청을 취소하지 않는다.
승인된 요청에서만 해당 대기 작업의 접수를 닫는다. 콜백 중 접수된 앱 이벤트는
거부된 경우 현재 콜백이 반환한 뒤 처리하고, 승인된 경우 종료 정책에 따라 취소한다.
콜백 예외는 앱 실패로 보존하고 이벤트 루프를 중단하며 정리를 계속한다.
소유 스레드가 아닌 곳에서 승인 질의나 실패 보고를 호출하면 `wrong_executor`로
거부한다. 호스트의 참·거짓 승인 어댑터는 이 경우 닫기를 거부하며 앱 상태와
이벤트 루프를 변경하지 않는다.
운영체제가 앱을 강제 종료하거나 프로세스를 중단하는 경우 이 콜백이 호출된다고
보장하지 않는다. 다중 창에서 마지막 창이 아닌 창의 일반적인 닫기는 이 앱 종료
콜백을 호출하지 않는다.

### 창별 종료 승인 계약

`Application` 안의 `Window(onCloseRequested: vm.canClose)`는 해당 창 스코프의 인자 없는
`() -> Bool` 콜백을 참조한다. 기본값은 허용이다. 게시된 창에만 콜백을
호출하고 게시 전 생성 실패와 운영체제의 강제 파괴에서는 호출을 보장하지 않는다.
콜백이 `false`를 반환하면 창과 앱 수명을 유지한다. 마지막 창은 창의 승인 후
앱 종료 승인을 순서대로 거친다. 같은 요청의 재진입은 거부하며 콜백 예외는
최초 수명 오류로 보존하고 이벤트 루프를 중지한다.

명시적 앱 종료 또는 운영체제의 앱 종료 요청은 열린 창을 선언 순서로 승인한 뒤
앱 승인을 질의한다. 어느 창이나 앱이 거부하면 닫기를 수행하지 않으며 파일·창
요청 접수도 유지한다. 모든 승인이 끝난 뒤에만 접수를 닫고 앱을 종료한다.
승인 질의 중 열린 창의 세대가 바뀌면 그 요청은 거부한다. 이미 승인된 마지막
창으로 인해 지연된 드라이버 종료에는 창 또는 앱 승인을 중복 호출하지 않는다.
콜백 내부에서 명시적으로 수행한 외부 부작용까지 되돌리는 트랜잭션은 아니다.

### 비동기 종료 확인

사용자가 저장 여부를 비동기로 선택해야 한다면 승인 콜백에서 확인 상태를 표시하고
`false`를 반환한다. 선택이 완료된 뒤 버튼 등의 인자 없는 이벤트에서
`quitApplication()`을 호출해 다시 요청할 수 있다. 이름 있는 개별 창의 닫기만
재요청하려면 `closeWindow("id")`를 사용한다. 이 명령들은 `Application` 안에서만
사용하며 다음 이벤트 루프 차례에 호스트 닫기를 요청한다. 중복 대기 요청은 하나로
합치고, 대기 중 종료되면 실행하지 않는다. 호스트의 닫기 요청은 같은 승인 콜백을
다시 거친다. 접수 실패는 호출 오류이며 접수 이후 호스트 오류는 앱 오류로 보존한다.

```lvui
Application(onCloseRequested: vm.canClose) {
    import vm DocumentModel
    Window { PushButton(text: "Close", onClick: quitApplication()) }
}
```

`onActive`와 `onInactive`는 iiGUI 주 호스트의 플랫폼 활성 상태를
앱 스코프에 전달한다. `onReady`가 성공하기 전에는 전달하지 않고 마지막 관측 상태를
보관하며, 준비 이후의 상태 전환은 순서대로 전달하고 같은 상태가 반복되면 다시
호출하지 않는다. 시작·준비 실패나 종료 후에는 전달하지 않으며 종료가 먼저 처리된
대기 이벤트는 폐기한다. 이벤트에서 재진입한 상태 변경은 현재 콜백 뒤에 처리하며, 한 번의
전달에서 64회 이상 다시 진입하면 오류로 중단한다. 콜백 예외도 오류로 보존하고 이후
활성 상태의 전달을 닫는다. 이 상태는 플랫폼별 애플리케이션·장면·최상위 창 신호를 반영하므로
각 운영체제에서 동일한 백그라운드 실행 권한을 뜻하지 않는다.
이 이벤트를 선언한 앱은 `IIGUI_HOST_APPLICATION_ACTIVITY_API`와
`Host::set_application_activity_handler`를 제공하는 iiGUI를 요구한다. 이전 헤더는
컴파일 오류로 거부하고, 이전 라이브러리는 새 함수의 링크 오류로 구분한다.

### 실행 인자 전달 명세

`Application(onLaunchArguments: vm.launch)`는 Core가 소유한 실행 인자 전체를
`const std::vector<std::string>&`를 받는 앱 스코프 콜백에 한 번 전달한다.
호출 기간에만 인자를 빌릴 수 있으며 이후 사용하려면 복사해야 한다. 인자 순서,
중복 및 빈 문자열을 유지하고 플랫폼에서 제공한 실행 파일 이름도 첫 항목에 포함한다.
직접 참조한 C++ 메서드의 반환값은 사용하지 않는다.

```lvui
Application(onLaunchArguments: vm.receiveLaunch) {
    import vm StartupModel
    Window { Label(text: vm.title) }
}
```

`StartupModel::receiveLaunch(const std::vector<std::string>& arguments)`는 앱의
명령행 정책에 따라 필요한 값을 복사하고 관측 상태를 갱신한다.

소유 스레드에서 `onStart`가 성공한 뒤, 네이티브 드라이버에 들어가기 전에 전달한다.
이벤트 예외는 시작 오류가 되며 `onReady`와 드라이버 진입을 막고 이미 시작한 앱의
정리를 계속한다. 같은 이벤트의 중복 호출 및 콜백 중 재진입은 거부한다. 파일이나
활성 상태 요청이 콜백 중에 접수되어도 `onReady`가 성공한 뒤에만 전달한다.
독립 뷰 빌드는 실제 앱의 진입 인자가 없으므로 이 이벤트를 발생시키지 않는다.

Windows의 Core 진입점은 명령행 UTF-16을 엄격한 UTF-8로 변환하며 다른 플랫폼은
`main`이 받은 바이트를 보존한다. 앱은 옵션과 파일·URL을 직접 해석해야 하며,
실행 인자 전달은 파일 연결 등록, 이미 실행 중인 프로세스로의 전달, 권한 획득이나
`onOpenFiles` 호출을 대신하지 않는다. 예를 들어 Linux 데스크톱 파일의
[`%F`](https://specifications.freedesktop.org/desktop-entry/latest-single/)는 여러
파일을 인자로 확장할 수 있으나 그 설정과 해석은 앱이 책임진다.

### 운영체제의 파일 열기 요청 명세

`Application(onOpenFiles: vm.openFiles)`로 운영체제가 보낸 파일 경로 묶음을 앱 백엔드에
전달한다. C++ 콜백은 `const std::vector<std::string>&`를 받으며 직접 참조한
메서드의 반환값은 사용하지 않는다.
이 값은 UTF-8 경로이며 URL이나 자동으로 열린 문서가 아니다. 경로의 읽기 권한,
문서 형식 판단과 열기는 앱이 책임진다. 실행 인자는 임의의 옵션을 포함할 수 있으므로
이를 파일 경로로 추측하지 않는다. 운영체제의 파일 형식 연결과 앱 배포 메타데이터도
앱이 별도로 설정해야 한다.

iiGUI가 전달한 파일 요청은 앱 소유 스레드에서 보관하고 최초 `onReady`가 성공한 후
도착 순서대로 묶음별로 전달한다. Cocoa 호스트는 대기 중인 네이티브 요청을 하나의
묶음으로 합칠 수 있다. 다른 앱 수명 콜백 도중 들어온 요청도 현재 콜백이 끝난 뒤
처리한다. 같은 경로의 반복은 제거하지 않는다. 각 묶음은 최대 256개 경로, 대기열은
최대 64개 묶음과 총 4 MiB이며 경로 하나는 NUL 없는 비어 있지 않은 UTF-8으로 최대
131072바이트이다. 빈 묶음은 무동작이다. 한 번의 전달에서 재진입이 계속되거나
입력·대기 용량이 잘못되면 오류를 보존하고 이후 파일 요청을 닫는다. 콜백 예외도
앱 실행 오류로 전달한다. 승인된 앱 종료 요청은 새 파일 요청을 거부하고 전달되지 않은
요청을 폐기한다. 이미 실행 중인 콜백은 반환할 수 있으며 그 콜백의 오류는 취소 중에도
보존한다. 앱 종료나 시작 실패도 전달되지 않은 요청을 폐기한다.

이 입력은 기존 iiGUI `HostCallbacks::files_opened`를 연결한다. 현재 확인된 전달
경로는 Cocoa와 UIKit 소스이며 Windows·Linux는 별도의 운영체제 파일 열기 전달이
구현되어 있지 않다. UIKit 호스트는 파일 URL을 제한된 대기열로 전달하며 잘못된
경로와 용량 부족을 호스트 오류로 기록한다. 보안 범위 접근이 승인된 URL은 호스트가
종료될 때 해제한다. 헤드리스 검사와 UIKit 소스 문법 검사는 플랫폼 이벤트의 실제
발생이나 파일 접근 권한을 증명하지 않는다.

생성된 앱 구성 코드는 iiSDKCore의 `Application`에 iiGUI 호스트와 LVUI 뷰를
연결한다. Core가 진입점·이벤트 루프·종료 순서를 소유하며 iiGUI가 네이티브
창을 제공한다. 앱은 LVUI 파서나 Qt, QML, LVRS를 실행 시 요구하지 않는다.
호스트와 뷰 등록은 Core의 원자적 구성 단위에서 함께 수행한다. 등록 실패 시
이번 시도의 드라이버와 부착 항목만 취소하고 기존 구성과 오류를 보존한다.
이 계약은 앱 등록에만 적용하며 외부 I/O나 독립적으로 제출한 작업을 되돌리지
않는다. 아직 구성이 끝나지 않은 상태에서 앱을 실행하지 않는다.
생성된 앱은 `IISDKCORE_APPLICATION_CONFIGURATION_TRANSACTION_API`와
`IISDKCORE_APPLICATION_BEFORE_DRIVER_API`를 제공하는 Core 헤더·라이브러리를
요구한다. 같은 버전 번호를 가진 이전 설치본이라도 기능이 없으면 컴파일 오류로
진단한다.

`lvui_add_application`은 앱 선언을 AOT 컴파일하고 Core의 앱 빌드 함수를 통해
진입 코드를 구성한다. 컴파일러만 사용하는 소비자는 iiGUI를 찾을 필요가 없다.
GUI 앱은 호스트 패키지를 직접 찾아 `iiGUI::iiGUI`를 제공해야 한다. LVUI의
빌드 함수는 iiGUI를 자동으로 검색하지 않는다.
스코프가 있는 생성된 앱 구성 함수는 선택적으로 스코프 설정 콜백과 백엔드
팩터리를 받을 수 있다. 예제를 직접 확장할 때는 각 백엔드 헤더를 `INCLUDES`에
지정하고 앱 대상의 헤더 검색 경로도 설정한다.

```cmake
find_package(LVUI CONFIG REQUIRED COMPONENTS Native)
find_package(iiGUI CONFIG REQUIRED)
lvui_add_application(MyApp SOURCE App/MyApp.lvui)
```

선택적 `NAME`, `INCLUDES`, `STYLE_FILE`, `STYLE_MODES`, `SOURCES`, `LIBRARIES`,
`OUTPUT_VARIABLE`은 생성되는 C++ 이름, 백엔드 헤더, 스타일, 추가 앱 코드·링크
대상과 생성 헤더 경로를 지정한다. 크로스 컴파일은 기존 `LVUI_HOST_COMPILER`
계약을 따른다. 리소스의 배포와 장치별 실행 검증은 이 함수가 대신하지 않는다.

### 데스크톱 앱 설치 명세

`lvui_install_application(MyApp DESTINATION .)`은 `lvui_add_application`으로
만든 데스크톱 앱의 설치 규칙을 추가한다. 설치는 명시적으로 호출하며 기존 빌드
트리의 앱을 수정하지 않는다. macOS에서는 `.app`과 그 비시스템 동적 라이브러리를
하나의 묶음으로 설치하고 [CMake BundleUtilities](https://cmake.org/cmake/help/latest/module/BundleUtilities.html)를
사용해 내부 참조를 재배치 가능한 경로로 바꾼다. Windows와
Linux에서는 앱 전용 디렉터리에 실행 파일과 비시스템 동적 라이브러리를 둔다.
Linux 라이브러리 경로는 앱 디렉터리를 기준으로 하며 설치 시 `patchelf`가 필요하다.
설치는 대상 운영체제에서 수행해야 하며 iOS·Android 앱 패키징은 지원하지 않는다.

```cmake
lvui_add_application(MyApp SOURCE App/MyApp.lvui)
lvui_install_application(MyApp DESTINATION Applications)
```

대상의 선언된 동적 의존성이 해석되지 않거나 서로 충돌하면 설치가 실패한다.
해당 의존성에서 Qt·QML·LVRS 라이브러리 이름이 발견된 경우에도 설치가 실패한다.
이는 정적 연결 코드나 동적으로 선택되는 플러그인까지 검사한 결과가 아니다.
운영체제 라이브러리, 그래픽 드라이버와 실행 중 동적으로 선택되는 플러그인·리소스는
자동 수집 범위가 아니므로 앱 제작자가 별도로 관리한다. 기존 설치 디렉터리는
병합되므로 배포 산출물은 비어 있는 별도 설치 접두사에 생성해야 한다. 외부를 가리키는
심볼릭 링크, 빌드 산출물과 겹치는 설치 위치 및 복사 대신 심볼릭 링크를 쓰는
`CMAKE_INSTALL_MODE`는 거부한다. 설치와 서명은 배포 검증의 별도 단계이다.
macOS의 선택적 `ADHOC_SIGN`은 로컬 검증용 임시 서명이며 Developer ID 서명과
공증을 대신하지 않는다. `DESTINATION`은 설치 접두사 안의 상대 경로이어야 한다.

## 검증 범위

두 구문, 스코프 소유와 입력 오류, 기존 창 루트 호환성, 생성된 C++의 컴파일 및
Core 수명 테스트를 확인한다. 이 검증은 OS 창, GPU, 실제 입력이나 모든 플랫폼의
실행을 검증했다는 뜻이 아니다.

2026-11-04 단일 창 앱 진입을 처음 추가한 시점에 macOS arm64에서 LVUI 전체 빌드와 헤드리스 회귀 검사 644건, 설치
및 패키지 검사 2건, 별도 iiSDKCore 앱 수명 검사 7건이 통과했다. 재배치한 설치
패키지로 두 구문의 앱을 각각 컴파일·링크했으며 실행하지 않았다. Qt와 LVRS SDK
접근을 차단하고, 검사 대상 패키지의 `qt.svg` 아이콘 자산만 예외로 허용했다.
생성된 앱과 주요 동적 라이브러리의 연결 목록에서는 Qt·LVRS를 발견하지 못했다.
검사에 사용한 iiSDKCore와 iiGUI는 작업 공간의 기존 스테이징 패키지이며, 이
기록은 다른 설치본이나 Windows·Linux 장치의 실행 결과를 대신하지 않는다.

같은 날 원자적 앱 구성 연결 후 Core와 LVUI를 다시 빌드하고, Core 헤드리스
검사 69건 및 LVUI 회귀 검사 643건과 재배치 설치·패키지 검사 2건을 통과했다.
구버전 Core에 대한 명시적 컴파일 거부와 새 Core의 오류·예외 롤백, 기존 등록
보존, 재진입 차단 및 LVUI 실패 후 재구성을 검사했다. Core의 기존 설치 기록은
보존했으며 새 Core는 `build/`의 별도 스테이징 패키지로 사용했다. 실제 OS 창과
GPU 실행은 포함하지 않는다.

재배치한 설치 패키지의 앱 컴파일·링크와 패키지 경계 검사가 포함된다. 앱 스코프의
드라이버 이전 활성화, 창 뷰 분리·재구성, 창 생성 실패, 활성 창의 조기 퇴역 거부,

앱 시작·준비·종료 이벤트를 추가한 뒤에도 같은 macOS 환경에서 전체 LVUI 빌드와
645건의 헤드리스·패키지 검사가 통과했다. 재배치 패키지로 두 선언 구문의 이벤트
앱을 컴파일·링크했으며, 콜백 순서와 중복·재진입 차단, 상태 전파, 오류 보존 및

다시 빌드하고 회귀 검사 645건을 통과했다. 재배치 설치 소비자, 패키지 경계,

준비 후 순서와 중복 제거, 재진입·대기열 한계 및 실패 후 정리를 검사했다. 검사
환경에서 Qt·LVRS 설치 경로를 차단하되 LVUI 리소스와 패키지의 `qt.svg` 아이콘
자산은 허용했다. 생성 앱의 직접 동적 연결 목록에 Qt·LVRS는 없었다. 실제 OS 창,

확인했고 Windows·Linux 경로는 소스만 이식했다.

같은 날 다중 창 생성과 창 준비 순서를 추가한 뒤 새 iiGUI 스테이징 패키지로
macOS arm64 전체 빌드와 LVUI 회귀 검사 647건을 통과했다. 재배치한 설치본에서
단일 창과 두 구문의 다중 창 앱을 컴파일·링크했고, 세 창 선언은 생성된 C++의
문법을 검사했다. 헤드리스 검사에서는 공유 앱 스코프와 창별 스코프, 창별 동적
속성, 지연된 닫힘, 취소 중 예외, 비동기 부착 오류와 정리 순서를 확인했다.
검사 환경에서 Qt·LVRS 설치 경로를 차단하되 LVUI 리소스와 패키지의 `qt.svg`
아이콘 자산은 허용했다. 생성된 macOS 앱과 확인한 Core 라이브러리의 직접 동적
연결 목록에는 Qt·LVRS가 없었다. 실제 OS 창·GPU·다른 플랫폼의 실행은 검사하지
않았다. iiGUI 경계 검사는 기존 HelloGUI 설정의 LVUI 의존성으로 별도 실패했다.

같은 날 보조 호스트의 준비 이후 오류 전달을 추가한 뒤 새 iiGUI 스테이징 패키지로
macOS arm64 전체 빌드와 LVUI 회귀 검사 647건을 통과했다. 재배치 설치 소비자,
패키지 경계, 다중 창, 장면 시작과 구버전 헤더 진단이 포함된다. 헤드리스 iiSDKCore
앱과 이벤트 루프에 준비 이후 호스트 오류를 주입해 원래 오류가 정리 후 앱 결과에
남는 것을 확인했다. 새 헤더와 이전 iiGUI 라이브러리를 함께 연결하면 누락된 실패
핸들러 함수의 링크 오류가 발생하는 것도 확인했다. 검사 환경은 Qt·LVRS 설치
경로를 차단하되 LVUI 리소스와 패키지의 `qt.svg` 아이콘 자산은 허용했다. 검사한

열림·닫힘 중 재진입, 콜백 실패와 최초 오류 보존, 두 단계로 중첩된 뷰의 종료,
다른 창으로의 공유 상태 전파를 헤드리스 검사에서 확인했다. 재배치 설치 소비자는
이벤트 유무가 다른 창들이 재사용 뷰를 공유하는 앱도 컴파일·링크했다. 창별
그래프 그룹과 바인딩 퇴역·콜백·재진입은 AddressSanitizer와

리소스와 설치 패키지의 `qt.svg` 아이콘 자산은 허용했다. 실제 OS 창·GPU·기기

같은 날 X11 전경 이벤트를 연결한 뒤 최신 iiGUI 스테이징 설치본으로 macOS
arm64에서 LVUI 선언형·마크업 앱 두 개를 컴파일·링크했고 수명주기 관련
헤드리스 검사 8건을 통과했다. 두 앱의 직접 동적 연결에는 Qt·QML·LVRS가
없었다. X11 호스트와 두 생성 앱, 전경 관련 검사 소스는 Linux aarch64 ELF
객체로 교차 컴파일했다. 해당 변경의 Linux 전체 라이브러리·앱 링크와 실제 X11
창 관리자·앱 실행은 확인하지 않았다. LVRS와 알려진 Qt SDK 경로를 격리
검사에서 차단하고 LVUI 리소스와 iiGUI 비교 문서는 검사 자료로 허용했다.
전역 설치본과 모든 간접 의존성은 검증하지 않았다. Wayland 전경 이벤트와
모바일 독립 다중 창은 여전히 별도 구현이 필요하다.

같은 날 동적 창 대상을 연결한 뒤 macOS arm64에서 선언형·마크업 생성 앱을
컴파일·링크했다. 헤드리스 검사는 중첩 파생값의 재진입 갱신, 이벤트 시점 선택,
대상 변경 후 지연 실행, 잘못된 이름, 인자 있는 이벤트와 창 퇴역을 확인했다.
해당 검사 번역 단위는 AddressSanitizer와 UndefinedBehaviorSanitizer를
통과했으나 연결한 SDK 라이브러리 전체를 계측하지는 않았다. 생성된 C++에서는
문자열 대상을 수용하고 `bool`·정수 대상은 거부하는 타입 검사를 통과했다.
Python 컴파일러 인터페이스도 두 선언 형식의 동적 대상을 생성했다.

두 생성 앱과 검사 소스는 Linux aarch64 ELF 및 iPhoneOS 18 arm64 Mach-O 객체로
교차 컴파일했다. 해당 변경의 Linux·iPhoneOS 전체 링크나 실제 운영체제 창·기기
실행은 수행하지 않았다. 모바일 독립 다중 창은 이 컴파일 결과와 별도로 미지원이다.
재배치된 LVUI 설치 패키지의 컴파일러·헤더로 두 동적 창 앱을 다시 생성하고
컴파일·링크했으며 앱은 실행하지 않았다. LVRS와 알려진 Qt SDK
경로를 차단한 환경에서 헤드리스 검사가 통과했다. 두 macOS 생성 앱에 대해 각각
시스템 외 arm64 Mach-O 파일 네 개의 선언된 동적 의존성을 재귀적으로 살펴보고
Qt·QML·LVRS 이름을 찾지 못했다. 시스템 공유 캐시와 실행 중 동적으로 선택되는
플러그인·드라이버는 이 검사 범위 밖이며 전역 설치본 전체의 독립성도 증명하지 않는다.

전체 회귀의 첫 실행은 662건 중 661건이 통과했고 전경 검사 한 건이 실패했다.
기존 LVUI 빌드가 참조한 과거 iiGUI 스테이징은 Cocoa 전경 기능 조회에 `false`를
반환했으며, 현재 iiGUI 빌드는 `true`를 반환했다. 최신 iiGUI를 별도 설치한
격리 구성에서는 전경과 동적 창 검사 두 건이 통과했다. 이전 스테이징은 보존하고
현재 iiGUI를 `iiGUI/build/lvui-lifecycle-stage-f0m5e8qw`에 별도로 설치해
LVUI의 기존 `build/`가 그 패키지와 헤더를 사용하도록 구성했다. 이 스테이징은
검증 시점의 스냅샷이므로 이후 iiGUI 소스가 바뀌면 다시 빌드·설치해야 한다.

최신 iiGUI 스테이징을 참조하고 상속된 레거시 라이브러리 검색 경로를 제거한
환경에서 전체 빌드를 마친 뒤, LVRS와 알려진 Qt SDK 경로를 차단한 상태로 전체
등록 자동 검사 662건을 다시 실행해 모두 통과했다. 이 구성에서는
`LVUI_STYLE_TOKEN_NATIVE_TESTS=OFF`이며, 재배치된 설치 패키지의 동적 창 앱
소비 검사와 전경·동적 창 헤드리스 검사는 포함된다. 실제 GUI 창은 실행하지
않았다.

재검사한 빌드 트리의 두 macOS 앱은 iiSDKCore 빌드 스테이징의 공유 라이브러리와
`~/.local/SDK/Vulkan`의 MoltenVK를 참조한다. 따라서 이 연결 검사는 배포용 앱
묶음이 해당 라이브러리를 자체 포함하거나 다른 Mac에서 독립 실행됨을 증명하지
않는다. 시스템 공유 캐시와 실행 중 선택되는 플러그인·드라이버도 의존성 추적
범위에서 제외됐다.

2026-11-05 데스크톱 설치 규칙을 추가한 뒤 macOS arm64에서 생성 앱을 빌드하고,
재배치한 LVUI 설치 패키지로 소비자 앱을 다시 빌드했다. 일반 설치와 `DESTDIR`
설치 각각의 `.app`을 검사했으며, 일반 설치본을 다른 위치로 이동한 뒤에는
앱을 포함한 비시스템 Mach-O 네 개의 선언된 연결이 모두 앱 내부에서 해결됐다.
iiSDKCore, iiSDKCoreObservation과 MoltenVK 원본 및 빌드 앱의 해시는 유지됐고,
임시 서명 검증도 통과했다. 잘못된 설치 경로, 외부 심볼릭 링크, 빌드 경로 중첩,
누락·충돌 의존성과 Qt 명칭 시험 라이브러리는 설치 전에 거부했다.

관련 설치·패키지·코드 생성·헤드리스 검사 7건과 최종 데스크톱 설치 검사 2건이
통과했다. Qt·LVRS SDK 경로를 차단하고 상속된 라이브러리 검색 경로를 제거했다.
Linux·Windows는 Apple 컴파일러를 사용하는 구성 단계에서 설치 규칙과 잘못된
서명 옵션 거부만 검사했다. 두 플랫폼의 바이너리 빌드·설치·실행, macOS의 실제
창·그래픽 실행과 Developer ID 서명·공증은 검증하지 않았다. 동적 플러그인과
시스템 라이브러리는 이동된 앱의 선언된 연결 검사 범위 밖이다.

같은 날 iiGUI UIKit 단일 창 호스트의 세션 연결·재연결을 보완했다. 해당 호스트와
LVUI 생성 앱 진입점은 Qt·LVRS SDK 경로를 차단한 환경에서 iPhoneOS 18 arm64
객체로 컴파일했다. LVUI 앱 진입점의 첫 컴파일은 iiColorManager 헤더 경로가 빠져
실패했고, 해당 경로를 지정한 재실행이 통과했다. iPadOS 전체 앱 링크·실기기
장면 전환과 독립 다중 창은 이 결과에 포함되지 않는다.

같은 날 UIKit 주 호스트의 닫힘을 Core의 조기 종료 신호에 연결한 뒤, 생성된
LVUI 앱의 창 백엔드가 드라이버 반환 전에 정리되고 `onStop`이 그 뒤 한 번만
전달되는 것을 헤드리스 검사로 확인했다. 관련 LVUI 헤드리스·코드 생성 검사
5건, iiGUI 콜백·장면·교차 컴파일 검사 10건, Core 앱 수명 검사 15건이 통과했다.
Core 앱 수명 검사 중 7건은 AddressSanitizer와 UndefinedBehaviorSanitizer로도
통과했다. Core iPhoneOS arm64 정적 라이브러리와 소비자 링크, iiGUI UIKit 소스의
교차 컴파일은 확인했으나 전체 iPadOS 앱 링크나 실기기 실행은 확인하지 않았다.
Qt·LVRS 탐색과 SDK 경로를 차단한 재배치 설치 소비자 및 공개 패키지 경계 검사도
통과했다. macOS 생성 앱 한 개의 직접 동적 연결 목록에는 Qt·LVRS가 없었다.

같은 날 후속 검증에서는 iPhoneOS용 Core·iiGUI·LVUI 정적 런타임을 새로 빌드하고,
공식 MoltenVK 1.4.2 iOS 정적 라이브러리와 생성된 다중 창 앱을 링크했다. 기본
장면 매니페스트와 두 UIKit 델리게이트 클래스가 앱에 포함됐고 직접 동적 연결에서
Qt·LVRS는 발견되지 않았다. 이 검증은 장면이나 앱 실행을 포함하지 않는다.
