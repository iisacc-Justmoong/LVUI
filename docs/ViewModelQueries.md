# ViewModel 객체 쿼리

상태: 기존 iiSDKCore 쿼리 계약을 바탕으로 2026-10-20에 채택한 LVUI 통신 설계이다.
아래에 명시한 기능은 Core에 이미 존재한다.
LVUI 멤버 어댑터와 바인딩 연동은 아직 설계 단계이다.

채택한 [AOT 컴파일 모델](CompilationModel.md)은 네이티브 뷰·VM 어댑터를 생성한다.
쿼리는 네이티브 객체 사이에서 런타임 값을 교환하며 LVUI 소스나 바이트코드를 실행하지 않는다.

<a id="selected-communication-rule"></a>

## 채택한 통신 규칙

ViewModel은 iiSDKCore 객체 쿼리로 값을 송수신한다.
다른 C++ 객체와 같은 객체 간 통신 모델을 사용한다.
쿼리는 읽기·쓰기·명령·응답·변경 알림을 다룬다.

`ii::runtime::QueryPort<Request, Response>` 계약과 다른 객체의 포트에 대한 명시적 참조를 사용한다.
VM은 요청을 받고 Model·Service를 쿼리한 뒤 선택한 결과를 수신하고 소비자에게 변경 쿼리를 발행할 수 있다.
포트는 VM 또는 같은 소유 스코프로 수명이 제한되는 어댑터에 속한다.

```text
뷰 바인딩·동작 어댑터 -> 쿼리 -> ViewModel
ViewModel             -> 쿼리 -> Model 또는 Service
Model 또는 Service    -> 값 응답 -> ViewModel
ViewModel             -> 응답·변경 쿼리 -> 뷰 어댑터
```

화살표는 통신을 설명한다.
Model·Service 소스 코드가 구체적인 ViewModel이나 LVUI 타입에 의존해서는 안 된다.
쿼리 계약은 적절한 의존성 수준에 둔다.

<a id="default-viewmodel-binding"></a>

## 기본 ViewModel 바인딩

ViewModel은 기본 바인딩을 제공한다.
뷰는 바인딩 어노테이션·래퍼 선언·별도 활성화 없이 VM 멤버를 직접 사용할 수 있다.
이는 [공통 반응형 값 모델](ReactiveState.md)을 따른다.
속성 읽기는 원본 VM 상태와 그 변경에 대한 실시간 의존성을 설정한다.
편집 가능한 컨트롤 바인딩은 멤버의 공개 쓰기 계약이 허용하는 경우 같은 원본에 변경을 전달한다.
읽기 전용 getter·const 멤버·도메인 검증의 기존 제한을 유지한다.

기본 동작은 다른 VM을 생성하거나 상태를 복사하거나 스코프 소유권을 변경하지 않는다.
AOT로 생성한 네이티브 어댑터는 바인딩을 Core 읽기·쓰기·변경 쿼리 계약에 연결하고
필요한 스코프 의존성만 유지한다.
컴파일러의 VM 역할 식별과 구체적인 컨트롤 바인딩 구문은 추가 구현 설계가 필요하다.
LVUI 기반 클래스나 수동 export 어노테이션은 요구사항으로 채택하지 않았다.

`@Observable`은 선택적 활성화 조건이 아닌, 관찰을 명시하는 선택적 표기로 유지한다.
일반 LVUI 변수도 새 VM 인스턴스가 되지 않으면서 기본 반응형 값 모델에 참여한다.
`@Static`은 설정된 수명 동안 값을 명시적으로 고정한다.

<a id="public-imports-and-view-notation"></a>

## 공개 import와 뷰 표기

기존 import 구문과 인스턴스 소유권은 유지한다.

```text
import vm CounterViewModel
```

공개 멤버는 계속 `@export` 없이 접근할 수 있으며,
private·protected 접근 제한과 C++ constness는 유지된다.
쿼리 전송은 이 규칙을 수동 export·멤버 등록 요구사항으로 대체하지 않는다.

`vm.value`, `PushButton(vm.increment)` 같은 표현식은 계속 뷰의 공개 멤버 표기이다.
UI 어댑터는 뷰 파일에 전송 세부사항을 노출하지 않고 읽기·동작을 쿼리 계약으로 매핑할 수 있다.
`.lvui`에 추가 쿼리 키워드나 저수준 `send`/`post` 구문은 채택하지 않았다.

`vm.increment`를 형성하면 연결된 메서드 참조를 만들며 호출 쿼리는 발행하지 않는다.
`PushButton(vm.increment)`는 컴포넌트의 입력 계약에 따라 해당 callable을 전달한다.
예제 버튼은 클릭 시 이를 호출하며 그 호출이 VM 쿼리를 시작할 수 있다.
`vm.increment()`는 표현식 평가 시 명시적으로 호출을 시작하고 결과는 선언된 타입을 따른다.
이벤트 의미는 컴포넌트에 속한다.
[메서드·콜백 의미](MethodReferences.md)를 참조한다.

일반 C++ 멤버에 필요한 매핑은 생성되는 브리지가 제공해야 한다.
동적인 `ObjectProperties` 트리는 사용할 수 있는 연동 경로이며,
자동 리플렉션이나 필수 수동 공개 멤버 허용 목록이 아니다.

<a id="payload-ownership"></a>

## 페이로드 소유권

- 작업에 필요한 값을 중심으로 요청·응답 타입을 정의한다.
- 선택한 값이나 명시적으로 소유하는 스냅샷을 반환한다.
  Core는 송신자·수신자·객체 전체를 페이로드에 자동으로 붙이지 않는다.
- VM은 LVUI 기반 클래스를 상속하지 않고 포트를 조합할 수 있다.
- 큐에 넣는 요청 타입은 Core의 복사 생성 가능 요구사항을 충족해야 한다.
- 명시적으로 공유한 불변 값은 페이로드가 될 수 있다. 차용 참조에는 여전히 유효한 수명 계약이 필요하다.
- 응답은 `void`, 도메인 결과, 스냅샷일 수 있다. 전송 성공과 도메인 작업 성공은 별개이다.

정확히 생성할 요청 타입과 뷰 측 인자·결과 변환은 정해야 할 구현 세부사항이다.

<a id="existing-property-query-operations"></a>

## 기존 속성 쿼리 작업

`ObjectProperties`는 `queries()`를 통해 수신 측을 노출한다.

| 작업 | 기존 목적 |
|---|---|
| `PropertyRead` | 요청한 값을 선택해 반환한다. |
| `PropertyWrite` | 수신 측 타입·접근·검증 규칙에 따라 값을 쓴다. |
| `PropertyInvoke` | 명시적 인자 값으로 메서드를 호출하고 결과를 반환한다. |
| `PropertyChange` | 변경 확정 후 수신 측에 변경 종류·경로·리비전을 알린다. |

`PropertyChange`는 새 값이나 객체 전체를 자동으로 포함하지 않는다.
수신 측은 선택한 최신 값을 요청할 수 있다.
사용자 정의 타입 지정 쿼리는 선언된 계약에 따라 새 값을 명시적으로 포함할 수 있다.

동적인 쿼리 가능·쓰기 가능·타입 정책은 계속 적용된다.
`ObjectProperties::apply()`는 소유자의 권한이며 정책을 우회하는 외부 지름길로 사용해서는 안 된다.
공개 C++ 멤버 브리지와 도메인 객체의 명시적 쿼리 API에는 각각 적절한 수신 측 계약이 필요하다.

<a id="execution-and-response-delivery"></a>

## 실행과 응답 전달

| Core 작업 | ViewModel에 관련된 계약 |
|---|---|
| `send(request)` | 호출자 스레드에서 동기 실행한다. 바인딩된 포트는 소유 영역 밖의 호출자를 `wrong_executor`로 거부한다. |
| 바인딩된 포트의 `post(request, completion)` | 설정된 `SerialQueue`에 넣으며 완료 콜백은 해당 수신 영역에서 실행한다. |
| `post(executor, request, completion)` | 바인딩된 수신 측의 실행기 검사를 준수하는 명시적 큐 전달이다. |

`post` 결과는 접수 여부를 나타내며 실행 완료나 도메인 결과 성공을 뜻하지 않는다.
취소·종료로 처리기와 완료 콜백이 억제될 수 있다.
완료 콜백이 UI 스레드에서 실행된다고 가정해서는 안 된다.

화면 상태 갱신은 소유 UI 실행 영역과 수신 스코프 종료 경계를 거쳐 돌아와야 한다.
다른 영역의 작업을 기다리며 UI를 막거나,
쿼리를 우회하기 위해 작업자 소유 변경 가능 상태를 직접 읽어서는 안 된다.

<a id="reactive-value-flow"></a>

## 반응형 값 흐름

읽기 계약으로 초기값을 얻는다.
변경 쿼리를 받으면 의존 바인딩을 무효화하고 필요한 최신 값을 얻는다.
같은 VM 인스턴스를 유지하며 매 프레임 모든 속성을 폴링하지 않는다.

Core 쿼리만으로 임의의 C++ 대입을 관찰하지 않는다.
언어의 기본 반응형 동작을 구현하려면 변경 처리기·생성된 접근 경로·관찰 기능이 적절한 변경 정보를 발행해야 한다.
이는 연동 의무이며 값마다 애플리케이션 수준에서 관찰을 활성화할 필요는 없다.
일반 공개 멤버 추적은 여전히 구현이 필요하다.

기본 VM 바인딩은 기존 원본의 읽기·쓰기·변경 계약을 사용한다.
[선언 어노테이션](DeclarationAnnotations.md)은 `@Observable`을 선택적인 명시적 표기로,
`@Static`을 값 안정성을 위한 표기로 유지한다.
바인딩 편집은 쿼리 계약으로 원본에 쓰며 VM 상태의 별도 복사본을 만들지 않는다.
정적 값은 설정된 전체 수명 동안 고정 값 보장을 유지한다.

Core의 기존 변경 처리기는 쿼리 수신 측이다.
암묵적인 UI 구독 레지스트리를 제공하지 않는다.
스코프를 따르는 LVUI 어댑터가 의존 바인딩을 관리하고 쿼리를 수신 측에 전달해야 한다.

<a id="errors-and-lifetime"></a>

## 오류와 수명

접수 거부·쿼리 전달 실패·처리기 실패·도메인 작업 오류를 구분한다.
`ObjectProperties` 응답은 전송 결과 안에 속성 작업 결과를 감싼다.

확정된 속성 편집은 `notification_error`를 별도로 보고할 수 있다.
값은 이미 바뀌었으므로 알림 실패만을 이유로 편집을 반복하지 않는다.

빌린 포트 참조는 소유자보다 오래 유지되어서는 안 된다.
파괴된 포트의 원시 참조가 쿼리 오류 처리만으로 안전해지지는 않는다.
대기 요청·활성 처리기·결과 전달은 VM과 같은
[스코프 종료 경계](InvocationLifecycle.md)를 따른다.

종료 시 새 요청을 거부하고 대기·활성 사용을 종료하며 UI 수신 측을 분리한다.
늦은 결과가 제거된 뷰나 새 활성화를 갱신해서는 안 된다.
오래된 결과 검사에 사용하는 요청 정체성·활성화 정체성·리비전은 명시적인 어댑터·페이로드 계약이며,
Core가 자동으로 넣지 않는다.

<a id="implementation-validation-targets"></a>

## 구현 검증 대상

- VM은 어노테이션이나 별도 래퍼 선언 없이 바인딩을 제공한다.
- 증가·초기화는 관찰 어노테이션 없이 `Label(text: vm.value)`를 갱신한다.
  비정적 지역 LVUI 변수도 변경을 전파한다.
- 편집 가능한 바인딩은 원래의 쓰기 가능한 VM 멤버를 변경하며, 읽기 전용 멤버는 계속 읽기 전용이다.
- VM은 타입 지정 요청을 받고 계약에 정한 값만 반환한다.
- VM에서 서비스로 보낸 요청의 결과는 VM 소유 실행 영역에서 적용한다.
- 카운터의 읽기·호출·변경·읽기 흐름은 VM 재생성 없이 레이블을 갱신한다.
- 실행기 오류와 접수 오류를 도메인 실패와 구분한다.
- 알림 실패는 확정된 증가를 반복하지 않는다.
- 뷰 제거 후 대기 요청·늦은 결과는 제거된 VM이나 대체 활성화에 접근할 수 없다.

이는 향후 LVUI 어댑터 검증 항목이며, 런타임 테스트 통과 결과가 아니다.
