# 뷰 선언과 C++ 뷰모델의 경계

LVUI의 목적은 뷰의 구성, 배치, 스타일, 표시 조건, 반복과 바인딩을 선언하는
것이다. 애플리케이션 객체의 타입·저장소·메서드 본문·업무 규칙은 C++이 소유한다.
LVUI 파일은 C++ 객체와 동작을 `import`로 가져와 뷰에 연결한다. 같은 원칙은
네이티브 AOT 코드 생성과 iiGUI 마운트에도 적용된다.
화면 상태 변경과 C++ 동작 연결을 위한 이벤트 스크립트는 `<script>` 태그 없이
같은 파일에 작성할 수 있다. 스크립트의 실행 계기는 명시한 이벤트이며 도메인
객체나 업무 메서드의 C++ 소유권을 바꾸지 않는다.
시각 컴포넌트와 배치·입력·렌더링의 목표 소유자는 iiGUI이다. 현재 LVUI에 남은
컴포넌트 구현과 전환 범위는 [그래픽 책임 경계](GraphicsBoundary.md)를 따른다.

```lvui
import vm CounterViewModel
Window {
    VStack {
        Label(text: vm.count)
        PushButton(text: "+", onClick: vm.increment)
        PushButton(text: "Reset", onClick: vm.reset)
    }
}
```

`CounterViewModel`과 `count`, `increment`, `reset`의 실제 선언과 구현은 C++에
있다. `vm.increment`는 나중에 전달되는 이벤트의 메서드 참조이고 `vm.increment()`는
평가 시 호출이다. 뷰를 생성하거나 다시 그릴 때 이벤트 참조를 실행하지 않는다.
뷰가 원본에서 읽을 계산값은 읽기 전용 C++ 멤버·메서드 또는 타입 지정 쿼리로
제공하고, 데이터 변경과 부수 효과는 C++ 명령에 둔다.

## 상태와 수명

뷰모델 소유 및 관측은 SwiftUI의 상태 중심 뷰 구성에서 개념을 빌린다. 뷰가
활성화되면 소유 import는 해당 스코프의 C++ 뷰모델을 한 번 만들고, 상태 변경과
재그리기는 그 인스턴스를 유지한다. 자식 뷰는 필요한 동일 인스턴스를 명시적으로
차용할 수 있다. 조건부 뷰가 퇴역하면 해당 스코프의 연결을 해제하고 소유 객체와
작업을 정리한다. 별도 활성화는 별도 소유 수명이다. 구체적인 생성·공유·차용은
[import 계약](TypeImports.md)과 [종료 계약](InvocationLifecycle.md)을 따른다.

| SwiftUI의 관리 개념 | LVUI와 C++에서의 대응 | 현재 범위 |
|---|---|---|
| `@StateObject` | 활성 뷰의 `import name Type`이 C++ 객체를 소유 | 활성화별 생성, 재그리기 시 유지 |
| `@ObservedObject` | 상위 소유 C++ 객체를 타입 지정 자식 입력으로 차용 | 전달과 수명을 명시해야 함 |
| `@State` | 화면에만 속하는 임시 표시 상태를 해당 활성화에 둠 | 앱·도메인 상태의 대안이 아님 |
| `@EnvironmentObject` | 공유 객체를 상위에서 자식에 명시적으로 전달 | 범용 계층 환경 주입은 아직 제공하지 않음 |

이 표는 소유·관측 관계를 비교하는 것이며 Swift의 속성 래퍼 문법이나 모든
SwiftUI의 동작을 그대로 제공한다는 의미는 아니다.

`ii::core::Observable` 같은 명시적 알림이나 쿼리 연결로 읽은 원본의 변경을
관측한다. 알림 없는 임의 C++ 필드를 자동으로 감지한다고 가정하지 않는다.
관측 가능한 값은 해당 값의 변경을 통해 갱신하며 매 프레임 뷰모델 전체를
폴링하지 않는다. 현재 일반 C++ 필드는 이벤트 명령 후 백엔드 revision을 통해
같은 백엔드의 일반 필드 바인딩을 함께 재평가하는 폴백이 있다. 이는 필드 단위의
선택적 갱신과 구분하며 변경 여부를 추정하지 않는 명시적 알림이 더 적합하다. 비동기
결과는 소유 실행 영역에 전달하고, 퇴역한 뷰에 늦은 결과를 반영하지 않는다.
SwiftUI 자체, Swift 런타임, Qt 또는 인터프리터에 대한 의존성을 뜻하지 않는다.

화면에만 속하는 펼침 여부 같은 일시적 표시 상태는 뷰 활성화가 보유할 수 있다.
문서·계정·작업·미디어 등 앱 전반에서 의미를 갖는 상태와 그 변경 규칙은 C++
뷰모델에 둔다. 색상·치수 상수와 재사용 `View` 선언은 뷰 구성의 일부이다.
LVUI 값의 기본 계약은 `@State`와 `@Bindable`이며, 실제 쓰기 권한과
명시적 `@Static` 예외는 [기본 반응형 값](ReactiveState.md)을 따른다.

## 현재 구현과 전환

스코프 소유 C++ import, 공개 멤버 바인딩과 메서드 참조는 구현되어 있다.
이벤트 블록은 뷰 상태 대입과 가져온 C++ 메서드 호출을 순서대로 실행할 수 있다.
호출의 수명과 접수 경계는 [즉시 선언형 View](ImmediateDeclaration.md)를 따른다.
LVUI는 객체 리터럴이나 이름 붙인 스크립트 본문을 선언하지 않는다. 객체 타입과
구현은 C++에서 정의하고 `import`로 연결한다. C++ 메서드 참조를 상수로 연결하는
것과 View의 콘텐츠를 선언하는 것은 메서드 정의가 아니다. 매개변수가 있는
재사용 View도 빌드 시 View를 구성하는 선언이며 일반 메서드 본문을 정의하지 않는다.

[검증용 카운터](../example/GettingStarted/CppViewModelCounter.lvui)는
[C++ 뷰모델](../example/GettingStarted/CppViewModelCounter.h)의 상태와 메서드만
연결한다. 네이티브 검사는 독립 활성화·반응형 갱신·퇴역을 다루며,
플랫폼 창이나 제품 앱의 실행 증거는 아니다.

macOS arm64에서 일치하는 iiSDKCore·iiGUI 테스트 패키지로 구성한 기존 `build/`를
사용하여 다음 검사를 수행했다. 생성된 위젯을 창 없이 검사한다.

```sh
cmake --build build --target LVUINativeViewOnlyTests
ctest --test-dir build --output-on-failure -R '^LVUI\.NativeViewOnly$'
```

별도 import·네이티브 메서드 참조·객체 전달·관측·쿼리·세션 검사 15건을 함께
통과했다. 다른 운영체제의 빌드와 실제 GUI 실행을 검증한 결과는 아니다.
