# C++ 접근과 런타임 계약

상태: 2026-10-20에 채택한 스코프 기반 백엔드 설계를 위한 지원 요구사항이다.
일반 반응형 스키마·쿼리 어댑터는 여전히 필요하다. 일부 컴포넌트의 실제 AOT,
C++ 동작 스코프와 자체 위젯 마운트는 [LVRSNative.md](LVRSNative.md)에 구현 범위를 명시한다.

<a id="native-execution-and-mounting"></a>

## 네이티브 실행과 마운트

LVUI는 [AOT 네이티브 컴파일](CompilationModel.md)을 사용한다.
컴파일 타임에 iiGUI의 자체 네이티브 C++ 위젯 코드와
Metal·DirectX/Direct3D·Vulkan 가속 코드를 대상 플랫폼에 맞게 빌드하여 iiGUI에 전달한다.
iiSDK 런타임은 이를 iiGUI의 네이티브 GUI·그리기 대상으로 마운트하고 실행·수명을 호스팅한다.
실제 C++ 위젯과 GPU 자원은 전달받은 네이티브 코드가 실행 시 생성한다.
iiGUI는 레이아웃·위젯 입력·상태·그리기를 소유한다. OS 어댑터는 창·단일 표시 표면·
입력 전달·IME·글꼴·가상 접근성을 연결하며 컴포넌트별 OS 컨트롤을 생성하지 않는다.
위젯 백엔드와 가속 경로의 구분은 [네이티브 위젯·가속 계약](CompilationModel.md#native-widgets-and-acceleration)을 따른다.
소스 표현식·어노테이션·동작 본문은 언어 인터프리터·바이트코드 VM·JVM·.NET/CLR 계층을 거치지 않는다.

이 문서의 런타임 동작은 네이티브 객체 활성화, 이벤트·쿼리 전달, 관찰, 그리기, 종료를 뜻한다.
네이티브로 컴파일된 디스크립터와 콜백은 애플리케이션 실행 중 언어 컴파일러 프런트엔드를
요구하지 않으면서 연동 정보를 제공할 수 있다.

<a id="public-interface-contract"></a>

## 공개 인터페이스 계약

import는 `@export` 없이 일반 C++ 객체의 공개 멤버에 대한 접근을 제공한다.
구현에는 스코프 소유 인스턴스를 생성하고 공개 인터페이스에 접근하며 올바르게 파괴할 수 있는
충분한 선언 정보 또는 생성된 브리지 정보가 필요하다.
AOT 빌드는 필요한 C++ 선언을 확인하여 네이티브 접근 코드를 생성한다.
탐색·코드 생성 방식은 구현 결정이며 애플리케이션 코드에 대한 수동 export 요구사항이 아니다.

| 정보 | 필요한 목적 |
|---|---|
| 타입 정체성과 공개 선언 | 가져온 백엔드와 공개 접근 가능한 멤버를 확인한다. |
| 생성 함수와 입력 계약 | 소유 스코프 활성화 시 새 인스턴스를 생성한다. |
| 대응하는 파괴 함수 | 올바른 소유자·모듈을 통해 인스턴스를 파괴한다. |
| 멤버 타입·C++ 접근성·constness | 공개 멤버 읽기·쓰기·메서드 호출을 검증한다. |
| 별도의 속성 변경 관찰 계약 | 관련 데이터 변경 시 반응형 소비자를 갱신한다. |
| 메서드 인자·반환 계약 | 인스턴스 메서드를 연결하고 호출한다. |
| 컴포넌트 입력·callable 계약 | 멤버 참조와 호출 결과를 컴포넌트의 선언된 입력에 따라 타입 검사한다. |
| 실행 영역·작업 소유권 규칙 | 올바른 영역에서 호출을 실행하고 결과를 전달하며 자원 사용을 종료한다. |

메타데이터를 캐시하거나 여러 인스턴스가 같은 타입 정보를 공유하더라도 생성·파괴는 계속 짝을 이룬다.
백엔드 코드는 이에 의존하는 인스턴스를 파괴할 때까지 사용 가능해야 한다.

private·protected 멤버는 계속 import를 통해 접근할 수 없다.
const 데이터와 읽기 전용 인터페이스를 쓰기 가능하게 만들지 않는다.
단순히 접근 가능하게 만들기 위해 개별 공개 멤버의 수동 등록이나 어노테이션을 요구해서는 안 된다.

C++ 선언의 가용성, 지원하는 타입 표현, 오버로드, 생성자 입력은 추가 구현 규칙이 필요하다.
선언 누락·지원하지 않는 변환은 export 표식 누락과 다른 진단이다.
이 설계에서는 그러한 표식을 요구하지 않는다.

<a id="mvvm-and-public-access"></a>

## MVVM과 공개 접근

LVUI는 애플리케이션 패턴으로 MVVM을 권장하며 ViewModel 상태 규칙은 SwiftUI를 참고한다.
ViewModel은 같은 규칙으로 공개 상태·메서드를 import하는 일반 C++ 클래스일 수 있다.
import에 LVUI 기반 클래스나 export 어노테이션은 필요하지 않다.

ViewModel은 기본 바인딩을 제공한다.
뷰는 바인딩 어노테이션이나 추가 래퍼 선언 없이 상태를 읽고 쓰기 가능한 멤버의 편집 바인딩을 직접 얻는다.
생성된 네이티브 어댑터가 바인딩·관찰 연동을 제공한다.
읽기·편집은 기존 VM 인스턴스를 대상으로 하며 읽기 전용 멤버는 계속 읽기 전용이다.

캡슐화는 C++ 클래스 작성자의 책임이다.
비공개 저장소를 공개 getter·setter·의도 메서드로 제공할 수 있다.
공개 접근이 모든 상태 필드의 변경 가능성을 강제하지는 않는다.
기본 반응형 값 모델 안에서도 소스 가시성과 네이티브 변경 알림 지원은 별개의 구현 책임이다.

<a id="properties-and-actions"></a>

## 속성과 동작

뷰에서 사용하는 비정적 값은 [기본 반응형 모델](ReactiveState.md)을 따른다.
`enabled: document.canSave` 같은 바인딩은 관련 원본 변경을 따라야 한다.
AOT·네이티브 브리지에는 멤버 접근 외에 읽기 추적과 변경 정보가 필요하다.
런타임은 각 의존성을 소유 원본에 연결하고 소유자 종료 경계에서 제거한다.
이 기능은 관찰을 선택적으로 활성화하는 것이 아니라 언어 기본 동작을 구현한다.

`document.save`는 연결된 메서드 참조이며 `document.save()`는 평가 시 명시적으로 호출한다.
`PushButton(document.save)`는 예제 컴포넌트의 콜백 입력 계약에 따라 해당 참조를 전달한다.
클릭 시 호출은 버튼 구현이 정의하며 언어가 이름으로 이벤트를 추론하지 않는다.
`Footer(status: document.status)`는 기본적으로 값과 그 변경에 바인딩된다.
멤버를 읽거나 메서드 참조를 재평가하는 것만으로 명령을 암묵적으로 실행해서는 안 된다.
명시적 호출은 호출 의미를 유지하며 결과를 수신 매개변수 타입에 따라 검사한다.
[MethodReferences.md](MethodReferences.md)를 참조한다.
일반 LVUI 변수를 포함하여 값 바인딩과 변경 추적이 기본 동작이다.
`@Observable`은 해당 의도를 명시할 수 있으며 `@Static`은 고정 값 예외를 설정한다.
구체적인 바인딩 투영·의존성 추적 API·허용 표현식 언어는 추가 구현 규칙이 필요하다.

[선언 어노테이션](DeclarationAnnotations.md)은 `@Static`도 제공한다.
초기화된 값은 설정된 수명 동안 바뀔 수 없다.
어댑터는 C++ 저장소가 우연히 변경을 허용한다는 이유로 쓰기 가능하게 취급하지 않고 고정 값 계약을 유지해야 한다.
정확한 수명 소유자와 정적 참조 의미는 추가 설계가 필요하다.

<a id="viewmodel-object-queries"></a>

## ViewModel 객체 쿼리

ViewModel은 iiSDKCore 객체 쿼리 값 교환에 참여한다.
수신 객체 소유 계약을 통해 읽기·쓰기·명령을 받고 선택한 값을 반환하며 변경 쿼리로 소비자에게 알린다.
VM은 다른 객체의 쿼리 포트를 사용하여 Model·Service 객체와 통신할 수 있다.

뷰의 멤버·동작 표기는 계속 어댑터에 노출되는 표면 구문이다.
공개 접근성, 쿼리 전송, 변경 관찰은 별개의 책임이다.
Core 계약과 채택한 LVUI 연동 규칙은 [ViewModelQueries.md](ViewModelQueries.md)를 참조한다.

<a id="existing-core-building-blocks"></a>

## 기존 Core 구성 요소

다음은 이번 문서 개정에서 검토한 현재 워크스페이스 소스 참조이다.
연동 후보이며 구현된 LVUI 어댑터가 아니다.

| Core 기능 | 관련 기존 계약 |
|---|---|
| `SDK/iiSDKCore/src/Runtime/Query.h` | 인스턴스 소유 타입 지정 요청·응답 포트이다. `send`는 동기적이며 큐의 완료 콜백은 수신 영역에서 실행한다. 취소 후 완료를 보장하지 않는다. |
| `SDK/iiSDKCore/src/Runtime/TaskScope.h` | 소유 콜백·캡처를 추적한다. 종료 시 대기 작업을 취소하고 활성 작업이 끝난 뒤 자원을 회수한다. 송신자는 소유자의 생존을 유지하지 않는다. |
| `SDK/iiSDKCore/src/Runtime/TaskScope.cpp` | 자신의 활성 작업 안에서 종료하거나 대기가 실행을 막는 문맥을 감지한다. LVUI 어댑터는 무조건 블로킹 종료를 호출하지 않고 안전한 종료를 조정해야 한다. |
| `SDK/iiSDKCore/src/Runtime/ObjectProperties.h` | 인스턴스별 속성 정의·정책·경로와 리비전이 있는 변경 기록을 제공한다. 임의의 C++ 멤버 쓰기를 자동 관찰하지 않는다. |
| `SDK/iiSDKCore/src/Plugin/Plugin.h` | 생성·파괴를 짝짓고 호출 거부·대기 작업 취소·활성 호출 대기·인스턴스 파괴의 종료 순서를 정의한다. |
| `SDK/iiSDKCore/src/Runtime/Runtime.h` | 작업 사이에서 상주 작업자와 고정 작업 슬롯을 재사용한다. 뷰 백엔드마다 런타임이나 작업자 풀을 만들 필요는 없다. |

플러그인 계약은 수명 관리의 참고 사례이다.
가져온 백엔드가 모두 동적으로 로드하는 플러그인이어야 한다는 뜻은 아니다.
Core 기본 요소를 재사용하더라도 뷰 바인딩·종료 어댑터는 여전히 필요하다.

`ObjectProperties`는 관찰·상태 연동 후보이며 자동 C++ 선언 탐색 기능이나
공개 멤버 접근을 위한 필수 수동 허용 목록은 아니다.

의존성 방향은 애플리케이션·UI 연동에서 Core 쪽으로 유지한다.
Core는 구체적인 애플리케이션 백엔드나 LVUI 언어에 의존해서는 안 된다.

<a id="resource-ownership-and-performance"></a>

## 자원 소유권과 성능

백엔드는 사용이 종료되고 파괴될 때 소유한 버퍼·핸들·타이머·작업 예약·기타 자원을 반환한다.
공유 실행기나 서비스에는 별도 소유자가 있으며 백엔드 하나가 제거됐다는 이유만으로 종료하지 않는다.

자원을 여전히 참조하는 네이티브·GPU 작업은 활성 사용으로 계산한다.
해당 사용이 끝나기 전에는 저장소를 해제하지 않는다.
할당자의 캐시 때문에 프로세스 RSS와 인스턴스 소유 예약의 논리적 해제량이 다를 수 있다.

파괴 후 메모리 저장소를 재사용할 수 있지만 새 import 활성화마다 객체 정체성과 상태는 새로 부여한다.
저장소를 재사용했다는 이유로 늦은 전달이 새 객체에 연결되어서는 안 된다.

클릭 사이에 백엔드를 유지하면 매 동작마다 생성·파괴를 반복하지 않는다.
이것이 레이턴시 보장을 뜻하지는 않는다.
스코프 활성화·메서드·속성 갱신·종료는 여전히 측정해야 한다.
생성자·소멸자의 작업량은 한정되어야 하며,
비용이 큰 작업은 UI 진행을 막지 않는 적절한 실행 영역을 사용해야 한다.

이 문서는 새 메모리 풀, 전역 백엔드 캐시, 뷰별 작업자 풀을 채택하지 않는다.

<a id="open-questions"></a>

## 미정 사항

- C++ 선언 탐색·브리지 정보 스키마·호환성 규칙.
- 현재 C++23/Cocoa 경로를 넘어서는 컴파일러 백엔드·네이티브 어댑터·디스크립터 형식.
- 현재 위젯 마운트를 넘어서는 다른 OS 입력·접근성 어댑터와 추가 가속 표면의 연동.
- 생성자 주입과 초기화 실패 처리.
- 관찰 가능한 속성·결과 전달 API.
- 공개 멤버·타입 지정 쿼리·값 바인딩 사이의 생성된 매핑.
- 컴포넌트 입력 스키마·callable 호환성·네이티브 콜백 표현.
- 실행 영역 귀속·호출 접수·스케줄링·취소 인터페이스.
- 비블로킹 종료 조정과 정리 오류 보고.
