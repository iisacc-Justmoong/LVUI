# 스코프 기반 백엔드 import

상태: 2026-10-20에 채택한 설계이다.
import는 활성 뷰·컴포넌트 스코프 동안 백엔드 인스턴스를 소유한다.
import 피연산자 순서는 아래와 같이 확정하며,
나머지 어휘 규칙과 런타임 API는 추가 구현이 필요하다.

<a id="import-contract"></a>

## import 계약

타입 청사진만 가져오는 형식은 `import class CppObjectName`이다. 이 선언은 C++ 타입 별칭을
생성하며 백엔드 객체를 만들거나 수명을 소유하지 않는다. 이름공간은 점으로 구분하며,
지역 타입 이름은 마지막 이름이다. `import class Domain.Model`은 지역 타입 `Model`을
제공한다. 같은 스코프의 값·객체 이름과 중복되면 진단한다.

실제 객체를 소유하는 아래의 바인딩 import와 구분한다. 임의 C++ 타입의 생성자 입력 및
사용자 View 조합 전체를 타입 별칭 하나로 지원한다고 간주하지 않는다. 생성자 의존성은
현재 [네이티브 생성 정책](BackendConstruction.md)을 C++ 활성화 진입점에 전달하여 연결한다.

```text
import bindingName CppObjectName
```

첫 번째 피연산자는 LVUI에서 인스턴스에 접근할 때 사용할 이름이다.
두 번째 피연산자는 C++ 백엔드 타입이다. 예시는 다음과 같다.

```text
import cpp Class
```

이는 `Class`로 생성한 인스턴스를 일반 지역 이름 `cpp`에 연결한다.
멤버는 `cpp.method`나 `cpp.property`로 접근한다.
이름 `cpp`는 자유롭게 정하며 특별한 import 모드를 뜻하지 않는다.

애플리케이션 예제도 같은 순서를 사용한다.

```text
import document DocumentBackend
```

`DocumentBackend`는 C++ 백엔드 타입이다.
공개 멤버는 `@export` 어노테이션 없이 가져온 이름을 통해 접근할 수 있다.
생성·파괴·멤버 바인딩에는 관련 C++ 선언과 호출 계약을 적용한다. 기본 생성 또는 앱이
전달한 타입 지정 생성 함수를 사용하며, 별도 import끼리 객체를 공유하지 않는다.

소유 뷰·컴포넌트 스코프가 활성화되면 import를 활성화하고 새 백엔드 인스턴스를 생성한 뒤,
가져온 이름 `document`를 해당 인스턴스에 연결한다.
사용을 종료하고 인스턴스를 파괴할 책임은 소유자가 유지한다.

[AOT 컴파일러](CompilationModel.md)는 import와 필요한 C++ 선언을 분석하여
네이티브 생성·멤버 접근·파괴 코드를 만든다.
소스 선언을 처리하는 동안 애플리케이션 백엔드 인스턴스를 생성하지 않는다.
백엔드는 컴파일된 소유 스코프가 활성화될 때,
의존 연결과 바인딩을 사용하기 전에 생성한다.

컴파일된 타입·바인딩 정보는 구현 선택에 따라 독립적으로 공유하거나 캐시할 수 있다.
이 정보는 런타임 소스 파싱을 요구하거나 별도의 import 활성화에서 생성한 인스턴스를 합치지 않는다.

<a id="instance-isolation"></a>

## 인스턴스 분리

별도의 import 활성화마다 자체 인스턴스와 변경 가능한 상태를 생성한다.
예를 들어 아래의 두 import는 독립적으로 소유하는 두 객체를 뜻한다.

```text
import leftDocument DocumentBackend
import rightDocument DocumentBackend
```

같은 뷰를 두 번 활성화해도 별도의 백엔드 인스턴스가 생성된다.
동일한 활성 뷰를 다시 그리거나 평가할 때는 기존 인스턴스를 유지한다.

위 두 선언은 이름 다음 타입이라는 확정된 순서로 인스턴스 분리를 나타낸다.
import에는 세미콜론 종결자를 사용하지 않는다.
세부 식별자 규칙과 줄 이어쓰기 규칙은 미정이다.

<a id="borrowing-and-child-views"></a>

## 차용과 자식 뷰

```text
AppControlBar(backend: document)
AppBodyView(backend: document)
```

두 자식은 같은 부모 소유 인스턴스를 사용한다.
현재 이 호출은 [타입이 선언된 재사용 View](Components.md)의 백엔드 매개변수로 구현한다.
`import class` 청사진으로 매개변수 타입을 지정하고 기존 import를 인자로 전달한다.
인스턴스 전달은 복사본이나 다른 백엔드를 생성하거나 소유권을 이전하지 않는다.
부모 스코프가 파괴를 소유하며 자식 바인딩과 콜백은 접근을 빌린다.

소유자가 닫힌 뒤에도 차용 접근을 호출 가능하게 남겨서는 안 된다.
자식을 제거하면 해당 자식의 연결과 구독을 해제하며,
부모나 다른 활성 사용자가 여전히 필요로 하는 백엔드는 파괴하지 않는다.

자식이 자체 import를 선언하면 해당 자식의 활성화가 소유하는 독립 인스턴스를 받는다.

<a id="choosing-the-owner-scope"></a>

## 소유 스코프 선택

import는 자신을 선언한 뷰·컴포넌트에 속한다.
창 수준 백엔드는 해당 창과 자식들에게 제공할 수 있다.
조건부 편집기에서만 사용하는 백엔드는 편집기 스코프에 둔다.

| 작업 | 인스턴스에 미치는 영향 |
|---|---|
| 소유 스코프 활성화 | 가져온 인스턴스를 생성한다. |
| 연결된 버튼 메서드 호출 | 기존 인스턴스를 사용한다. |
| 속성 재평가 또는 다시 그리기 | 기존 인스턴스를 유지한다. |
| 가져온 이름을 자식에게 전달 | 기존 인스턴스를 빌린다. |
| 차용하는 자식 제거 | 해당 자식의 사용을 제거한다. |
| 스코프를 유지한 채 뷰 숨기기 | 사용이 끝났다고 추론하지 않는다. |
| 소유 스코프 제거 | 종료를 시작하고 소유 백엔드의 사용을 종료한다. |
| 제거 후 새 스코프 활성화 | 해당 활성화를 위한 새 인스턴스를 생성한다. |

참조 가능한 살아 있는 import 바인딩은 미래 사용 경로이다.
마지막 텍스트상 멤버 접근이나 메서드 한 번의 반환만으로 객체가 더 이상 사용되지 않는다고 확정할 수 없다.

해제 조건과 종료 순서는 [InvocationLifecycle.md](InvocationLifecycle.md)에 규정한다.
import 활성화는 선언된 소비자들을 연결하기도 전에 즉시 객체를 버리는 것을 허용하지 않는다.

<a id="public-c-interface"></a>

## 공개 C++ 인터페이스

import는 지역 이름을 통해 객체의 공개 멤버를 사용할 수 있게 한다.
이 접근에 클래스·멤버 수준의 `@export` 표식은 필요하지 않다.

- 공개 데이터 멤버는 읽을 수 있으며, C++에서 변경을 허용하면 쓸 수 있다.
- 공개 메서드는 시그니처에 따라 참조하고 호출할 수 있다.
- private·protected 멤버는 import를 통해 접근할 수 없다.
- constness, 일반 C++ 멤버 접근성, 호출 호환성을 유지하며 import는 특권 접근을 부여하지 않는다.

`cpp.method`는 기존의 가져온 수신 객체에 연결된 메서드 참조이다.
`cpp.method()`는 표현식을 평가할 때 메서드를 명시적으로 호출한다.
둘 중 어느 표현식을 컴포넌트에 전달하더라도 수신 입력의 타입 계약을 적용한다.
호출 결과를 지연 호출로 자동 포장하지 않는다.
[MethodReferences.md](MethodReferences.md)를 참조한다.

공개 멤버 접근과 네이티브 변경 알림은 별개의 구현 책임이다.
뷰가 읽는 비정적 값은 [기본 반응형 모델](ReactiveState.md)에 따라 원본 변경을 따라야 한다.
구현은 값마다 관찰을 활성화하도록 요구하지 않고 해당 추적을 제공해야 한다.
생성·파괴·접근·관찰 기능은 [RuntimeContracts.md](RuntimeContracts.md#public-interface-contract)에 기술한다.

VM은 [Core 객체 쿼리](ViewModelQueries.md)를 통해 선택한 값을 송수신할 수 있다.
쿼리 전송도 같은 인스턴스 소유권·공개 접근 규칙을 유지한다.
빌린 포트 참조와 대기 요청은 소유 import의 종료 경계를 따라야 한다.

ViewModel로 사용하는 가져온 객체는 기본 바인딩을 제공한다.
뷰는 바인딩 어노테이션이나 래퍼 선언 없이 공개 상태를 직접 사용한다.
바인딩은 같은 소유 인스턴스를 참조하며 공개 읽기·쓰기 계약을 유지한다.
[기본 ViewModel 바인딩](ViewModelQueries.md#default-viewmodel-binding)을 참조한다.

빌드 시 C++ 선언 탐색과 네이티브 브리지 생성 방식은 구현 결정으로 남아 있다.
공개 멤버 접근을 허용하는 조건으로 수동 export 어노테이션이나 멤버별 등록을 도입해서는 안 된다.

<a id="open-questions"></a>

## 미정 사항

- 식별자 구문·이름공간·줄 이어쓰기·중복 이름 진단.
- 생성자 인자·의존성 입력·초기화 순서.
- 생성 실패와 일부만 활성화된 경우의 롤백.
- 조건부·동적 반복 뷰의 정확한 활성화 경계.
- C++ 선언 탐색·브리지 생성·메타데이터 캐시·백엔드 코드 유지.
- 구체적인 차용 핸들 표현과 만료된 접근의 진단.

별도 import는 프로세스 전역·세션 전역 백엔드 싱글턴을 암묵적으로 선택하지 않는다.
공유 사용은 기존 인스턴스를 전달하여 표현한다.
